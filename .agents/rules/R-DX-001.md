# R-DX-001: Errores seguros y diagnosticables

## Nombre
**R-DX-001:** Clasificar errores de carga, registrarlos y mostrar mensajes seguros.

## Alcance
- `frontend/src/App.tsx`
- `frontend/src/lib/error-utils.ts` y sus pruebas.

## Justificación
La carga de datos distingue fallos de conexión de errores de respuesta; la UI no debe revelar detalles internos. `App.tsx` delega el mensaje seguro a `getLoadErrorMessage`.

## Guía
- Mantén `getLoadErrorMessage(error: unknown): string` en `frontend/src/lib/error-utils.ts`.
- Mapea `TypeError` a conexión: `Error de conexión. Verifica tu red e intenta de nuevo.`; todo lo demás, incluido `!response.ok`, a servidor: `No se pudieron cargar los datos. El servidor respondió con un error.`
- Captura con `.catch((err: unknown) => …)` y ejecuta `console.error("[App] Error al cargar datos financieros:", err)` antes de `setError`.
- Nunca muestres `error.message` en la UI. Sin servicio de logging en el repo, `console.error` es el fallback permitido también en producción.
- Verifica: `npm --prefix frontend test` → passed; `grep -rn "error.message" frontend/src --include="*.tsx"` → 0 resultados.

## Ejemplo ✅/❌
✅ `.catch((err: unknown) => { console.error("[App] Error al cargar datos financieros:", err); setError(getLoadErrorMessage(err)); })`

❌ `catch (error) { setError(error.message); }`

## Excepciones
- Un servicio de logging incorporado al repo puede sustituir el fallback solo si registra el error técnico y no expone detalles en UI.

## Validación
- **Fecha:** 2026-11-19; **tarea:** `getLoadErrorMessage` + `.catch` en `App.tsx`.
- **Comandos:** `npm --prefix frontend test`; `grep -rn "error.message" frontend/src --include="*.tsx"`.
- **Resultado:** pruebas passed; cero referencias UI a `error.message`.
- **Refinado:** mensaje de servidor con concordancia corregida y categorías explícitas; logging de consola documentado como fallback de producción.
